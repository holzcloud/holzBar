## Planning-time evidence (2026-10-09, `MacOSX27.0.sdk` of the Command Line Tools, SDK version 27.0)

The planner already ran the scan by hand so the executor can cross-check its own run. This is evidence to compare with, not text to copy into the spike note (the note quotes the real run).

- The only public glass API is `NSGlassEffectView` (`contentView`, `cornerRadius`, `tintColor`, `style` regular or clear, `effectIsInteractive` from macOS 27), `NSGlassEffectContainerView` (`spacing`), `NSBezelStyleGlass`, and in SwiftUI the `Glass` type (`regular`, `clear`, `identity`, `tint`, `interactive`), `glassEffect`, `glassEffectID`, `glassEffectUnion`, `glassEffectTransition`, `GlassEffectContainer`, `glassProminent` and the glass button styles. All of them are things an app draws with; none reports or sets a system-wide clarity level.
- Public signals about transparency and contrast: `NSWorkspace.accessibilityDisplayShouldReduceTransparency`, `accessibilityDisplayShouldIncreaseContrast`, `NSWorkspace.accessibilityDisplayOptionsDidChangeNotification` (AppKit, macOS 10.10; the header says UI backgrounds "should not be semi-transparent; they should be opaque"), SwiftUI's `accessibilityReduceTransparency` and `colorSchemeContrast`, and the four `NSAppearance.Name.accessibilityHighContrast*` names. `NSApplication.PresentationOptions.disableMenuBarTransparency` is an option an app sets for itself, not a report.
- `Accessibility.framework`'s `AXSettings.h` lists no glass or transparency entry (it has `AXShowBordersEnabled`, `AXPrefersActionSliderAlternative` and others, none about glass).
- A sweep of every public framework header and Swift interface for glass, liquid, clarity, reducetransparency, increasecontrast and transparencylevel finds nothing else that is about the system's glass choice (the other hits are HealthKit glasses, Core Image filters and prose).
- Expected result: the scan exits 0 with `VERDICT: no public signal ...`, and the Decision line is `M27-04: not-applicable`.
