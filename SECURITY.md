# Security

holzBar is a menu bar manager that holds the Accessibility permission, so its security matters. This file says how to report a vulnerability, what holzBar promises, and which threats are known and how they are handled.

## Reporting a vulnerability

Please report vulnerabilities privately through GitHub's private vulnerability reporting, the preferred channel: on [holzcloud/holzBar](https://github.com/holzcloud/holzBar), open **Security → Report a vulnerability**. Do not open a public issue for a vulnerability; if you cannot use the form, open an issue that only asks for a private contact, without any details.

Only the latest release, and `main`, receive security fixes. holzBar is pre-1.0 (every 0.x release is published as a GitHub pre-release).

## What holzBar promises

- **No network.** holzBar never connects to the network. No networking code, no network entitlement; CI checks the sources and the built binaries.
- **Least privilege.** Accessibility at first launch; Screen Recording only when a feature that needs it is used. No entitlements, not even `com.apple.security.get-task-allow` (CI, the release and `Scripts/install.sh` fail on any), and the hardened runtime. holzBar is a single executable: it ships no nested code, such as a helper or an XPC service, that could run with its permissions.
- **Private logs.** Personal data (item names, bundle identifiers, profile names, paths) is logged as private or hashed.
- **Settings are input, not code.** Imported settings are decoded only as property lists and JSON, limited to holzBar's own keys with the expected type and range. A settings file, a URL command or a Shortcut never creates, changes or approves a script, and scripts run only from the folder the user chose, after the user approved their exact content.
- **Releases you can check.** Releases are signed with holzBar's own certificate and carry a GitHub build provenance attestation and SLSA Build Level 3 provenance; verify them against the release workflow and the tag ([docs/signing.md](docs/signing.md)). holzBar has no Apple Developer ID and is not notarized.
- **A guarded pipeline.** `main` accepts only pull requests with green checks, and a release is built only from a `v*` tag on `main`. Every GitHub Action is pinned by commit SHA and kept current by Dependabot; CodeQL runs weekly, OpenSSF Scorecard rates the repository, and secret scanning with push protection is on.

## Threat register

Severity follows the audits; no security, privacy or supply-chain finding of the audits was rated critical or high. The T-11 rows come from the security design of the scripts feature (Phase 11, written in the private planning repository): each gives the status of the scripts feature, which is a Preview until the maintainer has tested it on a Mac, and the test or check that proves it.

Keep the `workflow` scope out of agent and automation tokens. | T-06-L8 | Another local account swaps the app in `/tmp/holzbar-build` during `Scripts/install.sh` | Build from source | Low | Mitigate | **Mitigated**: builds in a private `mktemp -d` folder, removed on exit |
| T-11-H1 | An imported or synced settings file creates, alters or removes a rule that runs or asks a script | Settings import and export | High | Mitigate | **Mitigated (Preview)**: rules that use a script, the scripts folder, the approvals, the time limits and the profile hooks live only in `Scripts.json` on this Mac (mode 0600), outside the settings. The settings copy of the rules never holds a rule that uses a script, so an export carries none and an import neither brings nor removes one; a rule of an imported file that uses a script is dropped, and the import question says how many. A rule of the settings that has the identifier of a script rule of this Mac loses against it and is dropped (logged as a count), so a file cannot replace a script rule and the next save never deletes one; this Mac's rules are never cut by the rule limit. Proven by `ScriptStorageTests` (split and merge, script rules found in the settings left out and counted, an identifier collision, the limit, order) and `SettingsSchemaTests` (an imported rule list loses its script rules) |
| T-11-H2 | A URL command or a Shortcut creates, edits, approves or runs a script | URL scheme, App Intents | High | Mitigate | **Mitigated (Preview)**: no URL command and no intent can create, edit or approve a script, or name a script file. A URL command or a Shortcut can turn a rule that uses a script off, never on (the rule manager itself ignores such a request, so a rule changed while a question is open is covered too), and turning it off runs no end script. The engine pass after a change from outside asks no script condition and starts no script until the next event of the system, Check Now or a change you make in the settings, and a profile that a URL command, a Shortcut or the Focus filter applies runs no hooks. Proven by `AutomationEngineTests` (a pass from outside runs no end script, starts no script and leaves other rules alone); the URL and Shortcuts guards and the manager's hold are app code that the tests cannot reach yet, so they stay Preview until tested on a Mac. The price: a Shortcut cannot switch a scripted rule on |
| T-11-H3 | Untrusted values (a Wi-Fi name, an app name, an item title) become part of a command or a script's input | Script runner, rules | High | Mitigate | **Mitigated (Preview)**: no shell and no built strings. A script starts only from a launch plan that gives it its own file, no arguments (an AppleScript gets its own path and nothing else), no input, four environment names and one of five fixed event names in `HOLZBAR_EVENT`; no name, title or other value of holzBar reaches it, and a profile's name is never passed. Proven by `ScriptLaunchTests` (five events, exactly four environment names, no arguments, a name that is not plain gives no plan) and by `python3 .github/scripts/privacy-check.py processes`, which CI runs on every pull request: a process API, a shell path or the osascript path anywhere but the three lines of `.github/process-allowlist.txt` fails the build |
| T-11-H4 | A script that is not the one the user approved runs, and borrows holzBar's permissions: a link, a file that others can write, a downloaded file, a changed file | Scripts folder, script gate | High | Mitigate | **Mitigated (Preview)** by `ScriptGate`, checked again before every run: plain names only, no links, a regular file owned by the user and not writable by others, no quarantine, at most 1 MB, an executable with the owner's execute bit, in a folder that is itself safe (T-11-M6), and the full SHA-256 of the exact content the user allowed on a sheet that names the file and its folder (T-11-L5). A `.scptd` bundle is refused. Proven by `ScriptGateTests` and `ScriptStorageTests`; CI keeps every other file from starting a process (T-11-H3). **Residual risk, accepted:** malware running as the user can write the script, the rule and the approval too (`Scripts.json` is mode 0600, which does not stop a process of the user). The approval pins the content, not the interpreter a shebang names. A script's process may use holzBar's Accessibility and Screen Recording grants: that is assumed and not yet measured on a Mac, and until it is, treat an approved script as being as powerful as holzBar |
| T-11-M1 | A script file is swapped between the check and the run | Script store | Medium | Mitigate | **Mitigated (Preview)**: right before every run the file is opened once without following links, and its type, owner, mode, size, quarantine flag and SHA-256 all come from that one descriptor; a link, a pipe, a folder or a changed file is refused. Proven by `ScriptGateTests` (the decision over such facts; a changed file needs its approval again); the descriptor read itself is app code that stays Preview until tested on a Mac. **Residual risk, accepted:** the moment between the hash and the start of the process stays open, because a process is started from a path: a process that can already write the user's folder may swap the file in it |
| T-11-M2 | A script hangs, floods or forks without end | Script runner | Medium | Mitigate | **Mitigated (Preview)**: a time limit per script, 10 seconds by default and 1 to 60 in the pane; at the limit SIGTERM and, two seconds later, SIGKILL go to the script's process group (a child leads its own group, measured on macOS 27), and a script that runs too long counts as failed even when it exits 0 after SIGTERM. Output is read to its end into 64 KB per stream and the rest is dropped, and holzBar stops waiting one second after the script ended, so a flood or a background child that keeps the pipe open cannot grow memory or hold a run; the reader closes its end of the pipe itself after its last read, so a child that still writes cannot make holzBar read from a closed descriptor. One run per script at a time, at most ten condition checks and, counted apart so a burst of checks cannot starve a start or end script, ten other runs a minute (a run that is dropped for either limit, or because the script still runs, is shown in the pane as skipped), and a script condition is asked at most every 30 seconds per script; both are counted on a monotonic clock, so setting the clock back neither blocks scripts nor frees the limit. Proven by `ScriptLaunchTests` (limits of 1 to 60 seconds, only a clean exit is success), `ScriptOutputTests` (the cap) and `ScriptGateTests` (ten runs a minute for checks and for other runs apart); the kill and the output drain were exercised only in a development check of the real runner (a script with a noisy background child, 25 runs), not in a unit test. **Residual risk, accepted:** a script that forks and leaves its process group (`setsid`) survives the kill, and a process in an uninterruptible state outlives it until the kernel lets it go |
| T-11-M3 | A script's output is trusted: shown, opened or executed | Script runner, panes | Medium | Mitigate | **Mitigated (Preview)**: the pane shows a script's last result and the first line of its output as plain text on one line: control, format, bidirectional and private-use characters removed, at most 80 characters, shown verbatim and never read as a link, a path, a command or markup. The line is kept in memory for the session and never saved, logged or exported. Proven by `ScriptOutputTests`; the pane is Preview until tested on a Mac |
| T-11-M4 | A script inherits holzBar's environment and permissions | Script runner | Medium | Mitigate | **Mitigated (Preview)** as far as holzBar can: the script gets a minimal environment (`PATH`, `HOME`, `LANG`, `HOLZBAR_EVENT`), the scripts folder as working directory and no input, and the pane and the approval sheet say that scripts run as you with holzBar's permissions and that macOS asks separately before a script controls another app. What a script may do is not restricted beyond that: holzBar's hardened runtime does not apply to a process it starts. **Assumed, not yet measured on a Mac:** macOS attributes a process to the app that starts it, so an approved script may use holzBar's Accessibility and Screen Recording grants; holzBar does not claim otherwise. Proven by `ScriptLaunchTests` (environment) and the string catalog check for the wording |
| T-11-M5 | A rule or a profile changed from outside makes holzBar run a script | URL scheme, App Intents, Focus filter | Medium | Mitigate | **Mitigated (Preview)**: nothing a URL command, a Shortcut or the Focus filter changes makes a script run. A rule that uses a script cannot be turned on from outside; a change from outside holds scripts until the next event of the system, Check Now or a change you make in the settings, so the engine pass it causes asks no script condition and starts none; and a profile applied by a URL command, a Shortcut or the Focus filter runs no hooks and counts as no profile change for a script condition. Proven by `AutomationEngineTests` (outside-change cases); the guards in the URL, Shortcuts and profile code are app code that stays Preview until tested on a Mac |
| T-11-M6 | The Scripts folder itself is unsafe: a link, writable by others, or a synced folder where another Mac drops files | Scripts folder | Medium | Mitigate | **Mitigated (Preview)**: the scripts folder, the default one or one you chose in an open panel and confirmed, must be a real folder owned by the user that group and others cannot write to; with a link, a folder of another user or a folder others can write, nothing in it is listed or run, and the pane says why. An approval pins the exact content of a file, so a file that arrives later through a sync is not run until you allowed it. The folder is read with `lstat` on its path without a trailing slash: a first version of the check passed the path of a directory URL, which ends in a slash, and POSIX follows a link then, so the link could never be seen; the code review found it before release, and `ScriptGateTests` now make a real symbolic link and a real group-writable folder on disk and expect them refused. Proven by `ScriptGateTests` (safe and unsafe folders, a link first, a link and an unsafe folder on disk) |
| T-11-L1 | A script condition used as a poll burns energy | Automation engine | Low | Mitigate | **Mitigated (Preview)**: a script condition is asked on the events the engine already observes (power, network, running apps, displays, wake, profile changes) and by the Check Now button, at most every 30 seconds per script, never by a timer of its own. Proven by `AutomationEngineTests` (a rule with only a script condition observes power, network, running apps and displays and has no time source); the wake and profile-change events are app code that stays Preview until tested on a Mac |
| T-11-L2 | A script name spoofs holzBar's wording in the confirmation | Confirmation, Scripts pane | Low | Mitigate | **Mitigated (Preview)**: names with control, format, bidirectional, separator, private-use, surrogate or unassigned characters are refused; every name shown in the pane, the sheet, the rule sentences and the hook editor is cleaned and shortened like the names in URL prompts; the sheet's wording is fixed, names the file and its folder, and makes Cancel the default button. Proven by `ScriptGateTests` (deceptive names); the sheet is Preview until tested on a Mac |
| T-11-L3 | A damaged, crafted or newer approvals file runs scripts or is overwritten | Script store | Low | Mitigate | **Mitigated (Preview)**: `Scripts.json` carries a version and is written through a temporary file that is created with mode 0600 and then moved into place; the store is written before the settings, and the settings give up a rule that uses a script only once the store holds it on disk, so a failed write or a crash between the two loses no rule (the pane says when a write failed, and an export still carries none); a file from a newer holzBar is read-only and never overwritten, and nothing runs from it; a file that was read and is not a store is moved aside (an earlier set-aside file is kept) and a fresh, empty one starts, while a file that cannot be opened or read just now (no permission, too many open files, an I/O error) is left where it is, and nothing runs or is saved until holzBar starts again; decoding skips a single rule, hook or value it cannot read and keeps the rest (an older build drops such an element at its next save), refuses invalid values and cuts over-long lists. The approvals file of the betas is read once, for the move into `Scripts.json`, only when `Scripts.json` did not exist; the new file records the move at once (also a store that was set aside), so the file is not read again and a script rule of the settings is never taken in later. **Residual risk, accepted:** deleting `Scripts.json` by hand makes holzBar move the betas' data in again, which brings back approvals revoked since (they still bind the exact content of a file). Proven by `ScriptStorageTests` (a newer version and unreadable data are refused, an undecodable element is skipped, an open error is told from a file that is not a store, validation, caps, the one-time move); writing, moving aside and the mode are app code that stays Preview until tested on a Mac |
| T-11-L4 | Script names, output or paths reach logs, diagnostics, exports, URL answers or Shortcuts results | Logs, diagnostics, exports | Low | Mitigate | **Mitigated (Preview)**: holzBar logs only the status of a run and errors as private values, never a script's name, path or output; `python3 .github/scripts/privacy-check.py logs` (CI, every pull request) fails a log interpolation without a privacy level or one that makes names or errors public; the diagnostics count rules and name none; Shortcuts return rule names, never script names; scripts and their approvals leave the export (T-11-H1); a script's output line is kept in memory only. | T-11-L5 | The approval binds only the start of the checksum the confirmation showed | Confirmation, script store | Low | Mitigate | **Mitigated (Preview)**: the sheet is built from one read of the file, and the approval binds the full SHA-256 of what it showed: the store reads the file again and refuses, and refreshes the sheet, unless the full hash is the same. | T-11-L6 | A throwaway test app that was granted Accessibility to measure how a script's process inherits permissions keeps the grant | Development tooling | Low | Mitigate | **Mitigated by procedure**: the test app is never part of a release and is not built by CI; the measurement steps end by resetting its Accessibility and Screen Recording entries with `tccutil` and deleting it |
