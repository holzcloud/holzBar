# Security

holzBar is a menu bar manager that holds the Accessibility permission, so its security matters. This file says how to report a vulnerability, what holzBar promises, and which threats are known and how they are handled.

## Reporting a vulnerability

Please report vulnerabilities privately through GitHub's private vulnerability reporting, the preferred channel: on [holzcloud/holzBar](https://github.com/holzcloud/holzBar), open **Security → Report a vulnerability**. Do not open a public issue for a vulnerability; if you cannot use the form, open an issue that only asks for a private contact, without any details.

Only the latest release, and `main`, receive security fixes. holzBar is pre-1.0 (every 0.x release is published as a GitHub pre-release).

## What holzBar promises

- **No network.** holzBar never connects to the network. No networking code, no network entitlement; CI checks the sources and the built binaries.
- **Least privilege.** Accessibility at first launch; Screen Recording only when a feature that needs it is used. No entitlements, not even `com.apple.security.get-task-allow` (CI, the release and `Scripts/install.sh` fail on any), and the hardened runtime. holzBar is a single executable: it ships no nested code, such as a helper or an XPC service, that could run with its permissions.
- **Private logs.** Personal data (item names, bundle identifiers, profile names, paths) is logged as private or hashed.
- **Settings are input, not code.** Imported settings are decoded only as property lists and JSON, limited to holzBar's own keys with the expected type and range.
- **Releases you can check.** Releases are signed with holzBar's own certificate and carry a GitHub build provenance attestation and SLSA Build Level 3 provenance; verify them against the release workflow and the tag ([docs/signing.md](docs/signing.md)). holzBar has no Apple Developer ID and is not notarized.
- **A guarded pipeline.** `main` accepts only pull requests with green checks, and a release is built only from a `v*` tag on `main`. Every GitHub Action is pinned by commit SHA and kept current by Dependabot; CodeQL runs weekly, OpenSSF Scorecard rates the repository, and secret scanning with push protection is on.

## Threat register

From the security audit of 2026-10-03 (the private planning repository) and the full bug and security audit of 2026-10-05 (IDs F-…), with their fixes. Severity follows the audits; no security, privacy or supply-chain finding was rated critical or high.

| ID | Threat | Component | Severity | Disposition | Status |
|---|---|---|---|---|---|
| T-06-M1 | Another app or a web page turns Zen mode off with `holzbar://zen` and reveals hidden items during a screen share (confused deputy) | URL scheme, Zen mode | Medium | Mitigate | **Mitigated**: a URL may turn Zen mode on; turning it off asks first and is refused while the screen is shared; while Zen mode is on, no URL reveals items or changes a setting (`holzbar://search` and `holzbar://settings` are refused too from 0.0.7-beta2, F-07) |
| T-06-M2 | A crafted settings file crashes holzBar at every launch (`ItemSpacingOffset = 1e300`) or registers a hotkey without modifiers system-wide | Settings import | Medium | Mitigate | **Mitigated**: numbers are range-checked and clamped on import and load; stored hotkeys without a modifier, or with Shift alone, are not loaded |
| T-06-M3 | On macOS 27, Control Centre's camera, microphone and screen-capture indicator is gone while holzBar conceals items | macOS 27 concealment | Medium | Mitigate | **Mitigated for the microphone and the camera** from 0.0.7-beta2 (F-08): while it conceals items, holzBar puts a dot on its own icon (orange: microphone, green: camera), read locally from Core Audio and CoreMediaIO with no permission; on by default in Settings → General. **Disclosed for screen recording**, which no public API reports, in Settings → General (macOS 27) and the README. Control Centre's indicator itself cannot be kept: macOS removes it while any concealment assertion is live |
| T-06-M4 | A trojanized `holzBar.app` gets Accessibility because users re-grant it after every ad hoc update | Distribution, signing, TCC | Medium | Mitigate | **Mitigated for the main executable** from 0.0.6-beta1: releases are signed with a stable self-signed certificate and carry build provenance, so a main executable replaced and signed with another key loses the grants and macOS asks again. Up to 0.0.7-beta1 this did not cover the nested XPC service on macOS 26: a copy of the app with a swapped service kept the grants without a prompt (F-04, F-48; next row), and these docs called it mitigated (F-49) |
| F-04, F-48 | Code nested in a copied or modified `holzBar.app` runs with holzBar's grants (the menu bar item XPC service, macOS 26) | App bundle | Medium | Mitigate | **Mitigated** from 0.0.7-beta2: the XPC service is removed. holzBar ships a single executable and looks up each item's app itself, on a background queue with time limits. `Scripts/check-signature.sh` (CI, the release build, `Scripts/install.sh`) and the release's signature check fail on any other Mach-O file and on any `XPCServices`, `PlugIns`, `Helpers` or `Frameworks` folder |
| F-05 | A debugger attaches to holzBar and runs code with its grants: release and install builds up to 0.0.7-beta1 carried `com.apple.security.get-task-allow` | Build, release | Medium | Mitigate | **Mitigated** from 0.0.7-beta2: the builds turn it off, the release signs with empty entitlements, and CI, the release and `Scripts/install.sh` fail on any entitlement. Only Debug builds run from Xcode keep it |
| F-06 | macOS 26: another app's Accessibility frames claim a Control Center item window and make the camera and microphone indicator hideable | Item attribution, macOS 26 | Medium | Mitigate | **Mitigated** from 0.0.7-beta2: the camera, microphone, FaceTime and screen-recording items are never hidden, whatever app they are attributed to; apps signed by Apple are asked first; no other app gets a window while an app signed by Apple was skipped, and a window two apps claim belongs to none. Residual: code run by script hosts signed by Apple |
| F-09 | The Shelf's colour manager captures the screen while the Shelf is hidden, and on macOS 27 | Shelf | Medium | Mitigate | **Mitigated** from 0.0.7-beta2: it captures only while the Shelf is visible, and never on macOS 27 |
| F-11 | Missing or replaced signing secrets publish an ad hoc or differently signed release | Release workflow | Medium | Mitigate | **Mitigated** from 0.0.7-beta2: the sign job fails without the secrets, with any certificate whose SHA-256 is not holzBar's (`e55f0df1…`), and when the designated requirement differs |
| T-06-L1 | URL commands show a spoofable prompt, repeat it, or change lasting settings without asking | URL scheme | Low | Mitigate | **Mitigated**: prompts name only stored profiles, cleaned up and shortened; one prompt at a time and none for 30 s after a declined one; the Shelf and auto-rehide toggles ask first |
| T-06-L2, T-06-L3, T-06-L4 | Threats of the settings sync that 0.0.6 and the 0.0.7 betas carried: its file followed through symbolic links or read whole, an imported settings file turning sync on, the computer name written into the sync file | Settings sync | Low | Mitigate | **Closed** from 0.0.7: settings sync is withdrawn, so no code reads, writes, watches or mounts a sync folder, and the app has no sync key to turn on. Sync is planned for 1.0.0, redesigned from scratch, and its threats are assessed with it. Values that earlier builds stored in holzBar's own preferences (the chosen folder's bookmark, a random sync id, the salted hash of the hardware UUID) stay there, unused, and are never exported or imported |
| T-06-L5 | Custom icon data from settings reaches every image and document parser of AppKit | Custom holzBar icon | Low | Mitigate | **Mitigated**: decoded with ImageIO only as a few bitmap formats within byte and pixel limits; new icons are stored as PNG |
| T-06-L6 | The release job's write token is available during the whole build; actions pinned by tag; no binary checks on the published zip | Release workflow | Low | Mitigate | **Mitigated** from 0.0.7-beta2 (F-52, F-10): the release runs in separate jobs. The build job has a read-only token without persisted credentials, no secrets and no OIDC, and the project's SwiftLint phase stays skipped. The sign job holds only the certificate, has no token permissions and runs no code from the repository. Attestation, SLSA provenance and the release need no secret. Every action is pinned by commit SHA, and CI lints and checks the workflows. The signed zip's SHA-256 is compared from job to job and with the published asset before the cask changes |
| T-06-L7 | Minimal repository protections for `main`, `v*` tags and secrets | GitHub settings | Low | Mitigate | **Partly mitigated** (F-10): `main` accepts only pull requests with green checks; a release builds only a tag whose commit is on `main`; the cask is pushed only by the release workflow's deploy key, kept in the environment `release` that only `v*` tag runs can use, and the sign job runs in that environment too. **Residual risk, accepted by the maintainer on 2026-10-05:** the signing certificate and its password are still repository secrets, so a workflow file pushed to any branch by a credential with the `workflow` scope can read them, and the self-signed certificate cannot be revoked. Keep the `workflow` scope out of agent and automation tokens. They move into the environment `release` for the beta after 0.0.7-beta2 ([docs/signing.md](docs/signing.md#for-the-maintainer-add-the-secrets)) |
| T-06-L8 | Another local account swaps the app in `/tmp/holzbar-build` during `Scripts/install.sh` | Build from source | Low | Mitigate | **Mitigated**: builds in a private `mktemp -d` folder, removed on exit |
| T-11-H1 | An imported settings file creates or alters a rule that runs a script | Settings import | High | Mitigate | **Mitigated** (Preview): rules that run or ask a script are dropped from every import (`Defaults.validatedSettings`), and the approvals of scripts live in `ScriptApprovals.json` next to the Scripts folder, outside the settings, so no export, import or URL can create or approve one |
| T-11-H2 | A URL command or a Shortcut creates, edits, approves or runs a script | URL scheme, App Intents | High | Mitigate | **Mitigated** (Preview): no URL command or intent touches scripts; a URL can only turn a rule on or off, and the script still needs its own approval of its exact content |
| T-11-H3 | Untrusted values (a Wi-Fi name, an app name) become part of a command | Rules | High | Mitigate | **Mitigated** (Preview): no shell and no built strings; the script file is run with no arguments and no data from holzBar except the constant event name (`HOLZBAR_EVENT`) |
| T-11-H4 | A script that is not the one the user approved runs: a link, a file that others can write, a downloaded file, a changed file | Scripts folder | High | Mitigate | **Mitigated** (Preview) by `ScriptGate`: plain names only, no links, owned by the user, not writable by others, no quarantine, at most 1 MB, and the SHA-256 of the exact content approved by the user, checked again before each run. **Residual risk, accepted:** malware running as the user can write the approvals file too, and a file swapped between the check and the run is not excluded |
| T-11-M2 | A script hangs or floods | Script runner | Medium | Mitigate | **Mitigated** (Preview): SIGTERM after ten seconds and SIGKILL after two more, input and output discarded, one run per script at a time, at most ten runs a minute, a script condition is asked at most every 30 seconds and never by a timer of its own. The kill reaches the script's own process, not a process group |
| F-42 | Any app crashes holzBar on macOS 27 with a non-finite or huge Accessibility frame | macOS 27 item reading | Low | Mitigate | **Mitigated** from 0.0.7-beta2: such frames are rejected |
| F-46 | macOS 27: a spoofed theme-change notification discards all item images, so concealed apps flash into the bar | macOS 27 item images | Low | Mitigate | **Mitigated** from 0.0.7-beta2: images are discarded only when holzBar's own appearance really switches between light and dark |
| F-51 | macOS 27: the menu bar capture takes fragments of the window underneath as item icons when the bar is not on screen | macOS 27 item images | Low | Mitigate | **Mitigated** from 0.0.7-beta2: on a fullscreen space, with an auto-hiding bar, or when the screen reserves no height for it, the bar is captured only while it is on screen |
| F-53 | The documented attestation check accepts an attestation from any workflow on any ref | Signing docs | Low | Mitigate | **Mitigated**: the documented commands pin the release workflow and the tag, and only `v*` tags on `main` run the release workflow |
| F-54 | The "no Swift packages" CI check is bypassed by omitting `Package.resolved` | CI | Low | Mitigate | **Mitigated**: CI also checks the Xcode project's package references against the allowlist |

Still open from the audit of 2026-10-05, all low: F-43 (a spoofed screen-lock notification freezes concealment, Zen mode and item placement), F-44 (macOS 26: a process named like holzBar or Control Center gets their item tags), F-45 (macOS 27: a second process with the bundle ID `com.apple.MenuBarAgent` overwrites the system-item frames the click bridge uses), F-47 (item groups from a crafted import file are not capped) and F-50 (the 0.0.6 release notes' certificate check prints nothing). The audits' informational findings are accepted or tracked there.
